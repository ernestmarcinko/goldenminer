# Plan 15: Level cap 100

**Goal:** Raise the character level cap from 60 to 100 and re-tune the late-game XP curve so the extra 40 levels are a real climb, without disturbing the already-tuned early game. This is the foundation the passive-web rework (Plan 16) and the deeper economy depend on: a run can now reach level 100, worth 99 passive points instead of 59.

- **The cap.** `LEVEL_CAP` is a validation bound, not stored data: old saves keep working, and a level that was the ceiling simply stops being one. The only code that must change is the constant, the XP curve, and the places that read `LEVEL_CAP`.
- **The curve.** The early levels (1–30) are tuned and must stay exactly as they are. The ramp that is 1× through level 10 and 1.5× by level 30 continues rising past 30 so that 60→100 is a stretch rather than an afterthought.
- **Ascension.** Ascension stays available at level 60 — not at the cap — and becomes *more profitable the higher you level*, so there is a reason to push past 60 toward 100. The first ascension pays the depth-based points you already know; from the second ascension on, each 10 levels above 60 adds an ascendancy point (up to +4 at level 100).

**Architecture:**

- The change is almost entirely in `src/core/balance.ts`, `src/core/levels.ts` and the ascension files. `LEVEL_CAP` moves to 100; the XP ramp gains a second stage. `levels.ts`'s `xpToNext`/`gainXp` are already cap-agnostic and keep working. `ascendancy.ts`'s point formula and `ascend.ts`'s gate gain the level-60 unlock and the level bonus.
- The balance simulator (`src/core/sim.ts`) is the measurement tool. It currently assumes the cap is reached around day ~5 and stops there; it is re-targeted so the report measures the level-100 cap day and the ascension points (depth + the second-run level bonus), and its passive policy keeps spending through the new point budget.
- `save.ts` reads `LEVEL_CAP` only as a bound (lines 614, 690, 806, 808). No schema change, no migration: a saved level ≤ 60 is still ≤ 100, and a saved web still holds ≤ 59 points where 99 are now allowed.

**Tech stack:** unchanged — Node 24, TypeScript, Vite, React, Vitest. No new dependencies. No schema change.

**Spec:** main design §4.9 (pacing targets and the reference player) and §4.8 (ascension); `2026-10-26-plan-13-balance-and-launch.md` (the XP ramp and the reference-run simulator).

**Builds on:** Plan 14 (`dev-ernest` at `3c1ccf9`).

## Global Constraints

- Nothing under `src/core/` imports React or touches the DOM / `Date.now()` / `Math.random()`.
- **The early game stays put.** Levels 1–30 are tuned and must not change; only the curve *past* 30 is touched. The clear-rate test and every Plan 1–14 test stay green.
- **No schema change.** `SCHEMA_VERSION` stays 12; old saves load unchanged.
- **Readable numbers:** the UI already shows `level / LEVEL_CAP` from the constant, so the header follows automatically.
- Phones: no layout change; the header level bar just reads `… / 100`.
- Git: work on `dev-ernest`; stage explicit paths; short imperative commit messages; no attribution; never push.

## Review Focus

1. **The cap is 100, ascension gates on 60.** A `grep` for `LEVEL_CAP` shows only the definition, the simulator, `levels.ts`, `save.ts` (bounds) and the header. The ascend gate and Ascend tab read `ASCEND_LEVEL = 60`, and `ascend()` no longer checks the cap.
2. **The early curve is untouched.** `xpToNext(1..30)` is byte-identical before and after; a test pins it.
3. **The late curve and the ascension incentive are measured, not guessed.** The sim reports the level-100 cap day, the first-ascension points, and the second-run level bonus (+4 at 100); the balance test asserts the band and the bonus.
4. **Old saves load and play.** A level-60 save with a full 59-point web loads, gains XP again, and can allocate up to the new budget.

## Decisions this plan makes (my calls; overrule them in review)

| Topic | Decision |
|---|---|
| New cap | `LEVEL_CAP = 100`. |
| XP curve | Keep `XP_PER_LEVEL = 100`, `XP_EXPONENT = 1.5`. The ramp stays 1× through level 10 and 1.5× by level 30 (unchanged); add a second stage from 1.5× at 30 up to `XP_RAMP_CAP = 7.0` at level 100, applied linearly in the same style as the existing ramp. The tuned value is 7.0 (raised from 4.7 once achievements accelerated the late run), measured by the sim in Task 2. |
| Ascension unlock | `ASCEND_LEVEL = 60`: the Ascend tab opens at level 60, not the cap. The gate and the button read `ASCEND_LEVEL`, and `ascend()` checks it instead of `LEVEL_CAP`. |
| Ascension profit | `ascendancyPoints(deepest, level, priorAscensions)`. The depth term is unchanged (`floor(sqrt(deepest / 250))`). From the **second** ascension onward (`priorAscensions >= 1`), every `ASCEND_LEVEL_STEP = 10` levels above 60 adds 1 point (up to +4 at level 100). The first ascension has no level bonus, so a new player still ascends at 60 without pressure; later runs are rewarded for pushing higher. |
| Passive budget | A run now ends at 99 points (plus the ascendancy tree's). Plan 16 consumes this budget with more nodes; this plan only widens the budget and keeps `isPassives`'s bound (`LEVEL_CAP - 1 + MAX_ASCENDANCY_PASSIVE_POINTS`) correct automatically. |
| Cap-day target | The reference run should reach level 100 in roughly **1.5–2.5 simulated weeks** of the §4.9 schedule (the old 60-cap was ~5.3 days; the achievements boost in Plan 20 accelerates the idealized run, so the measured cap is ~12 days). Tuning reaches this by moving `XP_RAMP_CAP` only, then, if necessary, a single `monsterXp`/map-XP scalar — never the drop rates. |
| Save handling | No migration. `LEVEL_CAP` changes only the validation ceiling; the ascend gate moves to `ASCEND_LEVEL = 60`. |

### Task 1: The cap, the second ramp, and the level-60 ascension

**Files:** `src/core/balance.ts`, `src/core/levels.ts`, `src/core/ascendancy.ts`, `src/core/ascend.ts`; tests `tests/core/levels.test.ts`, `tests/core/ascendancy.test.ts`, `tests/core/save.test.ts`.

**Interfaces:**
- `LEVEL_CAP = 100`.
- Add `XP_RAMP_CAP = 7.0` (the tuned value: start at 2.25 and raise it in Task 2 until the cap lands in the target band) and a second ramp stage in `xpRamp`: the existing 1→1.5 over levels 10–30, then 1.5→`XP_RAMP_CAP` over levels 30–100. `xpToNext(1..30)` must not change; `xpToNext(30..100)` rises smoothly.
- `ASCEND_LEVEL = 60` and `ASCEND_LEVEL_STEP = 10`. `ascendancyPoints(deepest, level, priorAscensions)` returns the depth term plus the level bonus (`floor((level - ASCEND_LEVEL) / ASCEND_LEVEL_STEP)` when `priorAscensions >= 1`, else 0). `ascend()` gates on `ASCEND_LEVEL` and passes `state.level` and `state.lifetime.ascensions` before it increments the latter.
- No signature changes to `xpToNext` or `gainXp`; they already handle any cap.

**Tests:**
- Pin `xpToNext` for levels 1–30 to the current values (snapshot the curve before editing).
- `gainXp` levels 99→100, and caps XP to 0 at 100.
- `ascendancyPoints`: the first ascension (`priorAscensions` 0) gets no level bonus at any level; the second (`priorAscensions` 1) gets +0 at 60, +1 at 70, … +4 at 100, on top of the depth term.
- `ascend()` is refused below 60 and succeeds at 60 and above.
- A level-60 save with a 59-point web still validates and loads; a level-100 save round-trips.

**Step order:** snapshot the early curve → change the constants, the ramp, and the ascension logic → run `npm test` (only the sim/balance tests may need the Task 2 retarget) → commit `Raise the level cap to 100 and keep ascension at 60`.

### Task 2: Re-target the simulator

**Files:** `src/core/sim.ts`, `tests/balance/referenceRun.test.ts`.

**Interfaces:** the sim's stop rule changes from "stop at the 60 cap" to "run until level 100 (or `days` elapsed, default 24)". The passive policy already spends greedily and paths to Surveyor; it must keep spending through 99 points (alternate battle/mining, then toward the new keystones once Plan 16 lands — for now, toward the nearest allocatable notable). The report's `capDay` becomes the level-100 day; `ascensionPointsAtCap` is the depth term for the first run (no level bonus). A **second-run pass** ascends at 60 then runs to 100 again, reporting the level bonus so the incentive is measured, not assumed.

**Key tests:** `runReference({ seed: 12345, days: 24 })` prints the report; the balance test asserts the cap day lands in the 2–3-week band, first-ascension points ≥ 1, and the second-run level bonus at 100 is +4. Record the before/after in the measured table below.

**Step order:** change the stop rule and policy → add the second-run pass → run `npm run balance` → tune `XP_RAMP_CAP` (and, only if needed, `monsterXp`) until the band holds → record the table → full `npm test`/`npm run typecheck` → commit `Re-target the simulator for the level-100 run`.
