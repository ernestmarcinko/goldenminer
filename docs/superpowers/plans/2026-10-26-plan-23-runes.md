# Plan 23: Runes

**Goal:** Add runes — a second, exotic kind of socketable alongside gems. Ten kinds, each giving a *special* stat that gems cannot: a multiplicative or rule-changing bonus rather than a flat additive line. Runes are much rarer than gems, spread over an exponential rarity curve, and can drop from the very first metre at a fixed, static chance that no depth, level, or magic-find system touches.

- **A second socketable.** Today a gear item rolls up to 3 sockets and each socket holds a `Gem` (`{ gem, grade }`). This plan widens the socketed slot to `Socketed = Gem | Rune` and adds `RUNE_TYPES` (10 kinds) beside `GEM_TYPES`. A rune competes with a gem for the same 3 sockets.
- **Special, not bigger.** Gems add a flat value to an existing stat (`gemEffect` → `tierRange(...).hi`). A rune instead carries a multiplicative factor on a derived output (Gold, Souls, XP, dig power, damage, tick rate, critical damage) or a rule-changing flag (ignore hard rock, ignore hazards, chests drop one more, monsters attack slower). Nothing a rune does is expressible as a gem line.
- **Static drop, exponential spread.** When a gem would drop, an independent draw from the runes' own RNG stream upgrades it into a rune with chance `RUNE_DROP_CHANCE` — a single constant, unaffected by depth, magic find, or the `gem`/`map` feature rates. Given a rune drops, the 10 kinds are weighted by a geometric curve (kind 1 is 512× as likely as kind 10), so the overall "any rune" rate stays static while the deep kinds are exponentially rare.

**Architecture:**

- **Pure core first.** The rune catalogue, the effect table, the drop roll and the rarity curve live in `src/core/` with no React or DOM. `runes.ts` owns `RUNE_LABELS`, `RUNE_EFFECTS` and `runeTotals(state)`, which scans worn gear of both sets and returns the runes' multiplicative factors and flags. `stats.ts` and `battle.ts` apply those factors to the already-derived values; `dig.ts` and `combat.ts` read the flags.
- **Its own RNG stream.** The rune upgrade draw reads and writes a new `state.runeRng` (seeded from `state.rng` the same way `uniqueRng` is). On the common no-rune path the draw consumes only that stream, so `state.rng` and `state.nextId` are byte-identical to a build without runes; only an actual rune drop draws from the main stream to pick the kind. This is the exact idiom the uniques already use (`uniqueGen`).
- **Reuse the gem plumbing.** Runes stack and stash like gems: a `RuneItem` (`{ id, type: 'rune', rune, count }`) in the bag, and a Runes stash tab (`stash.runes: Record<RuneType, number>`, no grade dimension). The socketing flow, the loot filter, selling, salvaging, and the drop log all branch on the new `'rune'` kind beside `'gem'`.
- **One schema bump.** `SCHEMA_VERSION` 15 → 16; the migration adds `runeRng` and an empty `stash.runes`. The exact version is finalized by execution order (this is the next bump after the stats menu's 15).

**Tech stack:** unchanged — Node 24, TypeScript, Vite, React, Vitest. No new dependencies. One schema bump (15 → 16, finalized by execution order).

**Spec:** main design §4.9 (pacing/reference player) for where runes sit in the economy; the gem/socket system from Plan 7 (items and crafting) and Plan 10 (merchants/uniques, the unique-stream idiom); `src/core/items.ts`, `itemData.ts`, `stats.ts`, `itemGen.ts`, `dig.ts`, `combat.ts`, `save.ts`, `balance.ts`, `uniques.ts` as read for this plan.

**Builds on:** Plans 15–22 (`dev-ernest`): the schema-15 baseline (22), the gem/socket machinery (7) and the unique-RNG stream idiom (10). Runes is a new plan 23.

**Roadmap:** 15. level cap 100 · 16. the passive-web rework · 17. crafting overhaul and the ore economy · 18. character stats · 19. ascendancy tree expansion · 20. achievements · 21. the wiki · 22. the stats menu · **23. runes** (this plan) · 24. start screen · 25. skill-tree layout · 26. ascendancy-tree rebalance · 27. crafting rebalance · 28. mining animation · 29. ascendancy icons · 30. damage types and resistances · 31. unified equipment · 32. achievement notifications.

## Global Constraints

- Nothing under `src/core/` imports React or touches the DOM / `Date.now()` / `Math.random()`.
- **No `!` non-null assertions** in `src/` (the existing `?? []` and explicit checks stay).
- **The no-rune stream is byte-identical.** The rune upgrade draw uses `state.runeRng`, so a player who never finds a rune produces exactly the `state.rng` / `state.nextId` sequence a rune-less build would. The purity/determinism test pins this.
- **Static means static.** `RUNE_DROP_CHANCE` is a constant; nothing reads depth, level, magic find, the feature rates, or map modifiers to change it. A rune can drop from metre 1 and tier-1 kills.
- **No schema earlier than 16.** `SCHEMA_VERSION` is exactly 16 (the next bump after the stats menu's 15; the exact number is set by execution order). The migration (15 → 16) adds `runeRng` and a zeroed `stash.runes`; old saves load unchanged.
- **Tests stay green.** Every Plan 1–22 test keeps passing; the determinism test and the gem drop tests are extended, not weakened.
- Phones: the Runes tab and a rune card re-checked at 390 × 844; cells ≥ 44 px.
- Git: work on `dev-ernest`; stage explicit paths; short imperative commit messages; no attribution; never push.

## Review Focus

1. **The catalogue is 10 and special.** `RUNE_EFFECTS` has exactly 10 entries, each a multiplicative factor or a flag, none a flat `StatKey` line. A test walks all 10 and asserts the effect shape.
2. **The drop is static and separated.** A `grep` shows `RUNE_DROP_CHANCE` read only at the gem-drop sites, never scaled. The rune draw reads/writes `state.runeRng`; the determinism test proves a no-rune run is byte-identical before and after.
3. **The curve is exponential.** `RUNE_WEIGHTS` (or the geometric formula) sums to 1023 with kind 1 = 512 … kind 10 = 1; a test pins the weights and the `pickWeighted` outcome distribution.
4. **Socketing competes.** `GearItem.gems: Socketed[]` still honours `sockets`; `socketGem` generalises to `socketInto` and refuses when full. A rune and a gem cannot both exceed the 3-socket cap.
5. **Migration and validation.** A schema-15 save loads to 16 with `runeRng` and an empty `stash.runes`; the validator accepts a rune item/socket/tab and rejects a malformed one; the drop log and loot filter understand `'rune'`.

## Decisions this plan makes (my calls; overrule them in review)

| Topic | Decision |
|---|---|
| The 10 runes | Norse-named, one per special stat: `fehu` (Gold ×2), `uruz` (dig power and damage ×1.5), `thurisaz` (ignore hard rock), `ansuz` (Souls ×2), `raidho` (tick rate ×1.5), `kenaz` (ignore hazards), `gebo` (chests drop one more), `wunjo` (XP ×1.5), `hagalaz` (critical damage ×1.5), `isa` (monsters attack 20 % slower). Full table below. |
| Effect shape | `RUNE_EFFECTS[rune] = { mults?: Partial<Record<RuneStat, number>>; flags?: readonly RuneFlag[] }` where `RuneStat = 'gold' \| 'digPower' \| 'damage' \| 'autoTicks' \| 'souls' \| 'xp' \| 'critMultiplier'` and `RuneFlag = 'ignoreHardRock' \| 'hazardImmune' \| 'extraChest' \| 'slowMonsters'`. Multiplicative on the derived value (never re-entering the flat gear pool), flags read once at the point of use. A rune kind applies at most once however many copies are socketed. |
| Drop channel | The two existing gem channels: the `'gem'` metre feature (`dig.ts` `collect`) and map kills (`combat.ts` `onKill`'s `MAP_GEM_CHANCE`). **Not** chests — `rollChest` rolls gear only today, and keeping runes off chests leaves that roll untouched. A rune *replaces* the gem it would have been, so there is no rune without a gem draw. |
| Static rate | `RUNE_DROP_CHANCE = 0.005` (1 in 200 gem drops) — a single constant, drawn from `state.runeRng` only, so it never disturbs the loot stream. "Very rare but reachable": at the base `gem` feature rate (~1 gem / 33 m) the first rune lands in the low thousands of metres, possible from metre 1. The value is the tuning knob; the curve is fixed. |
| Exponential rarity | `RUNE_WEIGHT_BASE = 2`; the i-th kind (0-indexed, `fehu` first) weighs `2 ** (9 - i)`, i.e. `[512, 256, 128, 64, 32, 16, 8, 4, 2, 1]` (sum 1023). The weighted pick runs only *after* a successful upgrade draw, so the overall rate stays static while kind 10 is 512× rarer than kind 1. |
| Socketing model | Runes occupy the **same 3 sockets** as gems. `GearItem.gems` widens to `Socketed[]` (`Gem = { gem, grade } \| Rune = { rune }`); `GearItem.sockets` and `MAX_SOCKETS` are unchanged. Simplest clean choice: no new socket count, the existing socket dots/UI carry over, and "a rune competes with a gem" is the natural mental model for 3 slots. |
| Rune scope | A socketed rune's effect is **character-wide**, not per set: `runeTotals` scans worn gear of both sets. Runes are exotic enough to be universal, and this avoids a per-set effect matrix the catalogue does not need. They count only while the gear is worn, exactly as gems do. |
| Persistence | `RuneItem { id, type: 'rune', rune: RuneType, count }` stacks like a gem (`RUNE_BAG_STACK = 10`); a **Runes tab** `stash.runes: Record<RuneType, number>` (`RUNE_STASH_STACK = 1000`) — its own tab, not folded into Gems, because it has no grade dimension. `state.runeRng` is a `uint32` seeded `hash2(state.rng, 0x5e11)` (new games seed from the loot seed). `SCHEMA_VERSION` 15 → 16. |
| UI | Runes get their own rarity colour (a warm ember/orange) and a `rune` glyph sprite recoloured per kind via `PALETTE_OVERRIDES`, so a rune reads as exotic beside a gem. A socketed rune renders as a distinct dot (`data-rune`); the item card lists each rune's effect on a `'special'` tone; the Runes tab is one cell per kind. |
| Sell / salvage | A rune sells for `RUNE_SELL_GOLD = 500` and salvages into 1 `voidCrystal`; socketed runes are returned to the Runes tab by a socket reroll, and counted in an item's sell/salvage value the way socketed gems are. |

**Interfaces:**
- `export const RUNE_TYPES = ['fehu','uruz','thurisaz','ansuz','raidho','kenaz','gebo','wunjo','hagalaz','isa'] as const` and `export type RuneType = (typeof RUNE_TYPES)[number]`.
- `export interface Rune { rune: RuneType }`; `export interface RuneItem extends Rune { id: number; type: 'rune'; count: number }`; `export type Socketed = Gem | Rune`; `GearItem.gems: Socketed[]` (the comment becomes "socketed gems and runes").
- `balance.ts`: `RUNE_DROP_CHANCE = 0.005`, `RUNE_WEIGHT_BASE = 2`, `RUNE_BAG_STACK = 10`, `RUNE_STASH_STACK = 1000`, `RUNE_SELL_GOLD = 500`, `RUNE_RNG_SALT = 0x5e11`, and the rune salvage material (`voidCrystal`, 1).

- `stats.ts`: `deriveStats` reads `runeTotals(state)`, multiplies `goldMultiplier`/`digPower`/`autoTicksPerSecond` by the factors (then clamps as today), and returns `runeFlags` on `Stats`.

**Tests:** every `RUNE_TYPES` entry has a label and an effect; each effect is a `mult` or `flag`, none a flat `StatKey`; `runeTotals` over a crafted worn-gear state returns the right mults/flags, applies a kind at most once, and ignores a rune socketed in unworn gear; a rune's `gold`/`digPower`/`damage` factors move the derived stats by the expected factor; the weights sum to 1023 and are strictly geometric.

**Step order:** write the failing catalogue/effect tests → `items.ts`/`balance.ts` → `runes.ts` → `stats.ts`/`battle.ts` → `npx vitest run tests/core/runes.test.ts` → full suite → commit `Add the rune catalogue and its effects`.

- `dig.ts`: the `'gem'` feature calls `rollGemOrRune(state, tier)` instead of `rollGem`.
- `combat.ts`: the `MAP_GEM_CHANCE` kill drop calls `rollGemOrRune(state, tier)` instead of `rollGem`.
- Flags: `ticksForMetre` applies `HARD_ROCK_MULTIPLIER` only when the roll is hard rock *and* `stats.runeFlags` lacks `ignoreHardRock`; the hazard factor is 1 when `hazardImmune` is set. The `extraChest` flag adds one more `rollChest` item at the chest feature and one more chest in the treasure room.

**Key tests:** the determinism test gains a no-rune assertion — with `RUNE_DROP_CHANCE` forced to 0 (or a save with no rune drawn), `state.rng`/`state.nextId` are byte-identical to a rune-less run. `rollGemOrRune` returns a rune exactly at the drawn threshold and a gem otherwise, and never draws the main stream for the upgrade decision. `rollRune` honours the weights. The flags change `ticksForMetre` and the chest count as specified.

**Step order:** seed `runeRng` + `runeGen` → `rollRune`/`rollGemOrRune` → wire the two drop sites → the flags → run `tests/core/determinism.test.ts` and the drop tests → full suite → commit `Drop runes on the gem chance, statically, with an exponential kind curve`.
